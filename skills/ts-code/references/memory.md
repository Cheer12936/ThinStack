# 项目总览、切片档案、基线与恢复

新项目、正式切片计划、重要规则变更、项目建档或恢复任务时读取。记忆保存事实、决定和证据，不保存对话全文或内部推理。

## 创建入口与授权
- 显式入口：“使用 ts-code 建立/更新项目总览与切片记录”。默认只建档；不因此获得产品实现、测试执行或部署权限。
- 自动入口：新项目的首个结果及计划确认后，或既有项目新增业务已纳入确认计划后，创建/更新总览和每片记录；只有一片也可以登记。此前已明确授权直接实施时，复用该授权，不增加审批。
- 先找到唯一现行入口。已有 docs/SLICES.md、slice.md、其他索引或任务系统就沿用；多个入口冲突先查清谁负责什么，不覆盖或静默合并。
- 没有现行入口时，以[项目总览模板](../assets/project-overview-template.md)建立 docs/SLICES.md；在项目 README 或既有导航中添加入口。路径是默认值，不是开工门槛，不在技能安装目录记录业务项目进度。已采用机器档案的项目优先用 `project_state.py add` 一次完成编号、最小档案、路径登记和总览刷新。
- 纯讨论、只读审查不写文件。只设计允许产出所请求的设计文件，但不实现产品；未批准方案标记待确认，不能因为文件存在就执行。
- 小修复、文案/样式修改不为自己启动全项目建档；已有相关切片则关联修复和证据。用户明确要求记录时按请求保存。
- 无写权限时返回可保存的总览/任务快照，明确未落盘；缺少必要决定时暂停依赖工作，不声称下次必然记得。

## 什么时候设计切片
登记不等于详细设计，也不等于批准或交付。切片是有独立验收结果的一次工作，模块是长期职责范围，不能把整个“财会模块”天然视为一片。

| 场景 | 处理 |
|---|---|
| 新项目有多个结果 | 先复用已知决定，按[追问](clarify.md)解决影响架构和跨片依赖的重要未知；形成薄基线与完整范围的轻量切片图，只详细设计首个准备实施的结果。基础任务不冒充业务交付。 |
| 新增或改变用户可观察的业务行为 | 进入 SLICE；先澄清关键歧义，再定义当前行为、范围、模块理由、相关设计变化与证据。 |
| 新技术模块有独立可验证结果，或影响架构/跨模块契约 | 做对应的技术切片或影响设计；验收可为接口、兼容性或运行行为，不捏造用户界面。普通辅助函数归当前片，不按文件数拆片。 |
| 轮到后续已计划切片 | 核对依赖与相关基线，再补当前片设计；同一已批准范围不逐片重复确认。新的重要未决决定只阻止依赖部分。 |
| 当前规则、接口、身份/归属、范围因新事实变化 | 更新受影响的设计增量和基线；新业务结果另立关联切片，保留旧决定及证据，新增重要范围按授权规则处理。 |
| 明确 Bug、文案/样式、未变更契约的局部实现 | 保留短验收约定与按风险验证，不自动创建新片或重做全局设计。 |
| 恢复已有任务或查看进度 | 读取并核对记录，继续未完成步骤；设计仍充分时直接复用。用户明确要求设计时交付设计，不自动实施。 |

“新增财会模块”等会产生不同产品解释的需求先进入追问；查得出的事实自己查，不能以准备设计为由重复询问。设计深度随实际决定变化，不恢复固定十三章模板，也不强制 BDD/SDD/TDD 串行全走。

## 单一总览与每片永久档案
总览是客户和 AI 的共同入口，包含项目目标/本期范围、当前可用能力及环境、模块与切片地图、全量进度、阻塞/待决定、下一步和最近变更。每行链接该片唯一档案，不把全部历史塞进总览。
每个正式纳入计划的切片保留稳定编号和持久入口。沿用既有 SPEC/RUN 或独立章节；无既有布局时默认用 docs/slices/S-001.md 这类稳定路径，参照[任务模板](../assets/task-template.md)。新项目采用同一布局，不按项目大小切换模式；模板本身不填业务数据，不用一个“当前任务文件”覆盖前片。
后续片先留下编号、目标、依赖、阶段和批准范围的简短记录，不填未来的完整表结构或接口；当前片才展开必要设计。记录创建本身不代表批准。
既有 Slice N 或其他编号保留；新增取现行规则的下一号，已取消编号不复用，不按模块/会话重编号。完成或取消后保留档案；归档移动时同步所有入口，不删除历史证据或覆盖旧结论。

## 谁维护什么事实
- 总览维护项目目标、本期范围、里程碑和索引；进度表、阻塞摘要及统计从每片档案汇总，不成为第二份独立状态。
- 切片档案维护该片状态、为什么改、行为验收、模块及理由、依赖、批准范围、设计增量、检查结果索引和下一步。
- 基线维护跨片长期规则及决定；日志/测试工具记录实际检查证据。引用这些来源，不在多处重写同一规则。
- 先更新切片事实，再刷新总览摘要并核对一致性；若无法同步，标注总览待刷新及来源时间，不展示假实时进度。未采用机器档案时由代理按记录同步；采用时按[项目检查协议](../scripts/PROJECT_STATE.md)由脚本生成指定进度区，不手工维护第二套状态，不声称自动后台更新。
- 只在范围确认、切片开始/切换、重要决定、阻塞、验证完成或交接时更新；不因每个工具调用重写文件。任务登记、文档就绪与验收通过不可互相替代。

## 状态与客户可见进度
执行阶段可用：待澄清、待确认、已计划、开发中、待验证、已验证、已取消；沿用等义旧状态，不强制经过每个阶段。
阻塞作为独立字段记录原因、依赖与解除条件，不抹掉执行阶段。验证单独记已通过/失败/未验证/需重验及环境、被测版本、证据入口；部署和客户验收分别记录，不以 GREEN 推断已上线或客户已接受。
只把本期范围明确且证据仍适用的切片计入已验证汇总；取消/延后单列，历史通过但证据失效显示需重验。可报告“8 片中 3 片已验证”，不把数量比例当工作量或工期完成率。
一片通过不代表相关跨片旅程已通过；整体结论还须覆盖本次请求及必要联动证据。全项目、某版本和当前修复的范围须写明。

## 长期基线
沿用当前架构文件；没有时新项目用 docs/architecture/BASELINE.md，参照[薄基线](../assets/baseline-template.md)。已有 ARCHITECTURAL_BASELINE.md 不迁移、不建立第二份。
最少保存相关模块职责与依赖、统一术语、身份/数据归属、权限与重要不变量、决定及理由、来源/版本、批准状态和未决项。涉及模块设计时补其对外操作、结果、规则归属、隐藏的复杂性及关键失败行为；稳定契约只在基线或已有出处维护，切片引用变化。只写实际内容，不因样式修复补全架构。
从受影响代码、测试、schema 和配置核对事实；区分 OBSERVED（现状）、VERIFIED（已运行证明）、APPROVED（批准规则）、PROPOSED（建议）、UNKNOWN（未知）。读过测试不是运行证明，旧代码缺陷不是批准规则。
新项目或全局规则的依赖实现前保存确认的相关决定；已有项目只补必要差异。保留被替代决定及原理由，真正未决的安全/业务边界阻止相关实现，不以文件名或 READY 标签代替判断。

## 恢复、重开与安全
恢复顺序：总览 → 当前切片档案 → 相关基线 → 必要的依赖片/证据 → 核对代码与工作区。不要全读所有历史，已有有效批准继续生效。
文档保存的是决定与理解线索，不是“模型已理解”的证明；恢复时核对相关业务例子和代码，只有实质歧义或变化才再澄清。
交接保存当前片、已完成/失败/未验证、当前版本/工作区、模式切换事实、阻塞与下一步。后续修改只使受影响证据失效，未影响部分不重做。
已完成模块仅因新需求、真实故障、失效证据或相关规则变化重开，记录“原理由 → 新事实 → 修改决定”；旧 TODO、清理喜好或重新加载文档不构成重写理由。
外部并发改动先对比，不覆盖他人修改。客户可见总览与分享材料应脱敏；不写凭据、真实个人数据或内部推理，分享仍遵循授权。


## 可选机器化接入
项目明确采用时，在原档案添加小型 thinstack-slice JSON 块；配置仅列档案/总览/基线路径，不另存状态总账。旧档案不强制迁移，不支持的格式显示未检查。顶端机器块为当前状态、批准与正式验收的唯一来源；正文解释理由和设计，底部保留带时间/范围的历史，不再抄写一份“最新状态”。
正式验收从已确认档案读取，不能由证据报告自己删减；输入包含相关代码、测试、配置与基线，不包含自动进度区。总览只由这些来源派生。doctor 只读；sync 写入需授权，检查失败不冒充 GREEN。细节只在接入时读取项目检查协议。
登记未来片不自动绑定所有基线；实施前核对并绑定实际相关的已确认规则及输入。已有绑定和历史证据不得为消除告警而清空。`add` 遇未配置的旧入口会停止并要求适配；既有编号/目录只有一个明确序列时沿用，歧义时显式指定，不另起一套总览。
