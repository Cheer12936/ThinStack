# Project Initialization

PROJECT_INIT and SLICE describe the requested work, independently of DESIGN_ONLY / VERIFY_ONLY / DELIVERY and of both depths.

Before implementing a new project, present the structured baseline proposal required by SKILL.md and obtain the single confirmation defined in preflight-and-gates.md. Until approval, investigate read-only and produce requested design only. Do not interpret "initialize a project" alone as approval of unseen architecture/scaffolding decisions.

For a new project first discuss material gaps in product goal, actors, first-use scenario and initial scope. Focus questions on decisions that matter, not a fixed questionnaire; reuse explicit answers. Then decide the core identities, ownership, module dependencies and expensive global rules needed for the first useful slice and present the structured baseline proposal. Do not turn tentative brainstorming into approved architecture. One ARCHITECTURAL_BASELINE.md at the project convention's location, normally docs/architecture/, is sufficient; do not design every future entity or require a fixed collection of files.

When runnable initialization is requested, the Green Contract covers the minimal engineering foundation: launch/build, configured test harness and necessary infrastructure connections. The model chooses stack-appropriate proof. Initialize only infrastructure actually needed; do not introduce databases, auth systems, containers or CI without a task reason. A runnable foundation is not proof of business functionality.

For DESIGN_ONLY deliver the baseline and readiness/decisions; do not scaffold or execute migrations. For DELIVERY, resolve consequential architecture questions before dependent implementation and verify the agreed foundation. Record evidence/progress in the existing layout or an initialization RUN.md. Initialization GREEN is scoped to that foundation; keep planned business slices explicitly unimplemented.

For an existing project, baseline discovery is required before new business-slice implementation. Read the actual application entrypoints, module boundaries, models/schema and migrations, routes/contracts, auth/ownership enforcement, relevant tests, build/dependency configuration and external boundaries. Reuse existing docs after comparing their relevant claims with current code. Create a missing baseline or supplement stale/incomplete sections; avoid rewriting valid unrelated sections. Inspect code/config without copying credentials, personal data or environment secrets into the document; source paths/revisions suffice.

Distinguish OBSERVED (read in code), VERIFIED (supported by executed checks or other explicit evidence), PROPOSED (a future decision) and UNKNOWN. Record implemented architecture separately from desired rules. Bugs, contradictions and weak isolation found in code are findings, not automatically approved conventions. The baseline should cover the project's major modules/core rules while going deeper only into dependencies of the intended slices. Gaps outside the current slice may be labeled and deferred; consequential gaps affecting it block readiness.

Persist baseline status, version/date, covered scope, evidence/source paths, current revision/worktree context, approval source and open limits. Use DRAFT or BASELINE_NOT_READY while dependent decisions remain unresolved. Set BASELINE_READY only after the relevant architecture is coherent, approved and saved; this is architectural readiness, not proof that the whole system is bug-free or GREEN. If no write access exists, report persistence pending and do not begin dependent implementation.

Before each dependent slice, confirm its baseline prerequisites remain current; do not rerun whole-project onboarding for every slice or session. Present changed consequential decisions for confirmation once, reusing previous valid approval. Baseline and the mapped slice plan may be approved together; after approval save/update the baseline before implementation. Approved code-derived documentation work does not authorize fixing unrelated findings, resetting data or replacing the architecture.

The narrow exception is a local well-understood fix restoring existing behavior: it may reference the applicable contract/code and explain why project-wide baselining is unnecessary. A request to onboard/document the existing project explicitly still requires the baseline; a new feature cannot be relabeled as a fix to evade the gate. Read-only reviews remain read-only.

When the request includes several business outcomes, show the lightweight slice map alongside the initialization proposal; baseline preparation is not a substitute for decomposition. Continue into all slices covered by the approved map without repeated confirmation. A new feature outside that plan needs its own structured proposal and confirmation. For each later slice link applicable baseline rules, detail only the current delta, and update the baseline only if a global rule changes.
