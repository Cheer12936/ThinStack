# 测试驱动开发（TDD）

在实现前决定是否采用，而不是实现后补测试却称为 TDD。
优先用于可复现缺陷、确定性业务规则、权限/金额/库存/状态转换等可自动验证且回归成本高的行为；用户明确要求时遵循。
单纯视觉、文案和探索性原型不强制测试先行，但必须按改动给出有效观察。一次性或原型不豁免数据、资金或安全要求。

## 一个行为一个反馈循环
先写表达批准行为的测试，运行并确认因目标行为缺失/错误而失败；再最小实现使其通过；必要重构后重跑受影响检查。
测试运行器损坏、导入错误、无效数据夹具不算行为失败。暂时无法形成有效失败时记录原因与替代证据，不冒充完成测试先行。
预期结果来自用户/业务规则，不从当前实现倒推出“正确答案”。避免实现和测试共享同一个未经核对的错误假设。
尽量复用项目现有测试工具；不要为了一个样式修改安装整套框架。不要求所有测试层都出现，也不把每个函数都变成独立模拟单元。
不得跳过必要失败、削弱有效断言、只为特定夹具硬编码，或把真正要验证的边界模拟掉。测试确有缺陷或需求变化才修订，并记录理由。
先做最快可信检查，再做必要集成/回归；通过单元测试不代替数据库、权限执行位置、真实接口或并发证据。
测试通过后按当前约定停止；新代码影响已有证据时才重跑。相关安全问题、真实回归或项目必跑检查失败仍然阻止完成。

弱模型使用短循环，强模型可自主选择内部实现策略；两者都不能自创业务正确性或省略必要证明。
