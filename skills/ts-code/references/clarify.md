# 追问与行为澄清（BDD）

用途：类似“Grill Me”的设计访谈，但只把**会导致做错产品**的部分问透。采用决策树式收敛，不追求把整个未来系统一次问完，也不依赖外部 Grill Me 技能。

## 触发
当以下任一项存在多种合理解释，且不同答案会改变当前产品方向、业务切片或高代价决定时触发：
- 谁使用、为谁负责；
- 用户要完成什么结果、从哪里开始、在哪里看到结果；
- 关键业务规则、权限、数据归属或状态变化；
- 第一阶段范围、成功条件或外部边界。

像“新增一个财会模块”这类只有领域名、没有角色和业务结果的需求，应先进入追问。
明确 Bug、文案、样式以及已有规则下非常清楚的小功能不触发。

## 提问算法
1. 先读取用户已给信息、当前验收约定、薄基线、代码和可用资料；能自行查明的事实先查，不让用户代查，也不重复已回答的问题。
2. 把仍会改变方向的未知项视为一个决策树。先解决上游决定，再问依赖它的下游决定；不要随机扫问题清单。
3. 默认**一次只问一个问题**。只有几个问题强耦合且拆开会让用户更难回答时，才合并为一小组。
4. 每题优先提供 **2–4 个具体、互斥度较高的常见选项**，允许用户给自定义答案。避免空泛的“是/否”或开放式大问，除非问题本身确实适合。
5. 对每个选项只说明会影响决策的主要后果；信息足够时给出一个**推荐项及理由**，但不得把推荐当成用户决定。
6. 用户回答后，用一句话确认新决定并更新决策树，然后立即处理当前最重要的下一节点；不要重复总结全部历史。
7. 若新答案暴露权限、金额、历史数据、生产迁移等高风险边界，按主技能提高相应设计/验证深度，而不是继续靠提问替代证据。
8. 用户只批准“继续调查/按这个方向设计”不等于批准尚未展示的实现；已有同一具体方案授权也不重复索取批准。

## 问题优先级
优先问会造成最大返工或产品分叉的问题：
**业务结果/角色 → 关键规则与归属 → 状态/权限/数据边界 → 当前切片范围 → 次要交互与实现偏好。**

例如“新增财会模块”，先问“第一阶段主要服务哪类业务结果”，而不是先问导出格式、页面颜色或字段命名。

## 退出条件
满足以下条件就停止追问，进入设计/实现：
- 能用一个正常示例说明角色、起始状态、操作和可观察结果；
- 适用时能说明一个关键边界、拒绝或失败示例；
- 负责模块及其修改理由可以写入当前验收约定；
- 剩余未知只影响可逆实现细节，不会改变当前切片、重要契约或高代价决定。

示例可用“给定／当／那么”，也可用自然语言。重要词在验收、模块、接口和数据记录中保持同义；发现词汇冲突时先解决含义。

## 记录与边界
把用户答案、关键决定、理由与行为示例写回**同一份当前验收约定**；会跨任务长期成立的规则再写入薄基线，不额外制造一份重复 BDD 文档。
对不阻塞当前切片的未知标记假设；安全边界和重要业务决定不能为减少提问而擅自猜定，暂时无法确认时只暂停依赖部分。

追问只能建立设计共识，不能替代真实用户需求验证、实现测试或生产证据；结束追问不代表功能 GREEN。
