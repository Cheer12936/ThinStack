# 追问与行为澄清（BDD）

用途：类似“追问我”的访谈，但只解决影响产品行为的重要歧义；不是所有任务的开场仪式，也不依赖外部 Grill Me 技能。

触发：谁使用、什么结果、权限/数据归属、关键成功条件存在多种合理解释。新项目不必然触发；明确 Bug、文案和样式不触发。
先用已给答案和现行业务规则排除歧义；能从代码或资料查到的事实先查，不让用户代查。已有事实不要重复问。
一次提出一个最能区分方向的问题，或少量紧密相关的问题；给出可理解的选择、影响和建议，而不是问几十个开放问题。
不能把用户同意“调查一个方向”当成批准未见的实现。用户已明确授权当前方案时，不重新征求相同批准。

## 退出条件
能够用一个正常示例及适用的边界/拒绝示例，说明角色、起始状态、操作、结果和关键规则；剩余未知不会改变当前切片或高代价决定，就结束追问。
示例可用“给定／当／那么”，也可自然语言。重要词在验收、模块、接口和数据记录中保持同义；词汇冲突明确解决。
把答案、决定依据与验收示例写回同一当前约定，长期规则写入基线；不额外制造一份重复 BDD 文档。
对非阻塞未知标记假设；安全边界和重要业务决定不能为节省询问而擅自猜定。暂时无法确认时只暂停依赖部分。

## 边界
访谈和行为示例不能代替真实用户需求验证，也不能单独保证实现正确。输出只承诺共识与验收定义，不声称测试已执行。
