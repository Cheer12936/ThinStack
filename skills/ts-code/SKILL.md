## 1. 范围、授权与用户可见性
- 遵循宿主权限及项目规则。只设计/只审查不修改产品；只验证可执行已授权检查，但不擅自修复产品。
- 新项目、新业务功能默认先展示关键方案并确认一次；同一具体方案已获批准或用户明确要求直接实施，不重复确认。
- 方案按[内容底线](references/proposal.md)覆盖会影响交付的实质信息，章节可合并。待确认时仅进行只读调查及请求的设计。
- 新增范围、改变重要业务规则、破坏性操作、生产写入或付费调用需相应授权；常规本地实现授权不包含这些操作。
- 开工用一句中文显示工作类型、执行方式与本次结果，例如“薄栈｜修复｜自主：恢复回访列表，不改变权限规则”。
- 仅在切片切换、验证增强或阻塞时更新进度；交付说明实际结果、证据与剩余项，不用步骤数量制造进度感。

## 2. 任务分流与风险
工作类型与授权范围相互独立；路由不自动授予修改权限。

| 内部类型 | 用户看到的工作方式 | 必要产物 |
|---|---|---|
| FAST_FIX | 修复：恢复清楚的既有行为 | 短验收约定与直接故障证据；不启动全项目规划 |
| PROJECT_INIT | 新项目：确定首个可用结果与最小基础 | 薄基线、首片路线与基础运行证据 |
| SLICE | 切片：交付一个业务或独立技术结果 | 相关基线增量、当前验收约定与切片证据 |

多个独立结果按业务拆片，不按前端/后端/数据库拆片；只详细设计当前片。共用基础能运行不等于业务已交付。
保留既有编号和总览入口（包括已有 slice.md / SLICES.md）；没有时默认 docs/SLICES.md，不另建同义总表。
初始化项目或新业务纳入已确认计划时，按记忆规则创建/更新总览及每片持久记录；明确要求项目建档时也触发，纯讨论/只读审查不落盘。
先登记目标、依赖和状态，轮到当前片实现前才补齐行为、边界与验收设计；新增业务、独立技术结果或重要契约变化需设计，普通小修复不重做规划。已有充分设计直接复用，后续片不预写完整规格。

设计与验证各自使用 LIGHT / STANDARD / FULL（轻量/标准/强化），默认不逐次报告标签：
- 设计由重要未决决定与影响范围决定；验证由实际失败后果决定。代码少不等于风险低。
- 小修复通常轻量；普通切片通常标准；核心身份、架构或全局契约变化需强化设计或明确影响分析。
- 权限、金额、历史数据与破坏性公共接口变更需强化验证；新写/修改生产迁移至少标准设计、强化验证。
- 强化不等于跑所有测试。仅验证实际受影响边界，合并重复检查。
- 新证据可调整深度，但不能删掉仍然必要或失败的检查。风险提高时向用户说明具体原因。

## 3. 长期基线与当前验收约定
开始依赖实现及恢复任务前，从总览定位当前片，再读其档案、相关基线和必要依赖证据并核对代码；模型上下文不是持久存储。
新项目、正式业务切片或重要规则改变，按记忆规则保存薄基线和当前记录；每片有稳定入口，完成后保留，不被下一片覆盖。小修复不强制建档。
当前验收约定（Green Contract）至少说明：为什么改、可观察行为、负责模块及选择理由、不能破坏什么、用什么证明。
已有 SPEC.md / RUN.md / 架构文件继续使用，不复制并行版本。切片状态以其档案为准，总览按档案汇总；验证通过、客户验收和上线分别记录。建议、现状、批准规则和已运行证据不能混为一谈。

## 4. 自主与引导
- 默认自主：只约束当前结果、边界和证据，由模型选择工具、实现策略与合理验证间隔。
- 用户要求引导，或已知本任务的能力评测支持引导时进入引导；不按品牌固定强弱名单。
- 出现无关扩改、重复无效修复、遗忘修改理由、通过测试但违背验收等可观察信号时，保存当前状态并切入引导。
- 缺凭据、工具不可用、测试环境坏了不等于模型变弱；隔离阻塞，不能靠增加提示词或降低标准冒充恢复。
- 引导缩小当前行为和修改步长，不降低验收、权限或风险底线；恢复稳定后可在切片边界返回自主并简述理由。
- 这是执行指令，不是独立监控器；无法可靠验证时停止相关交付，不保证识别服务端模型变化。

## 5. 按需采用行为、规格与测试方法
- 初始化先对齐跨片高代价决定，再细化当前片；已知事实不重复问，可逆实现细节后置。
- BDD（行为驱动开发）用于形成共同认可的行为示例，不等于填写固定句式；SDD（规格驱动开发）只写当前关键决定与接口边界。
- TDD（测试驱动开发）在实现前决定是否采用：可复现缺陷、确定性业务规则及可自动验证的高风险行为优先测试先行，或遵循用户明确要求。
- 文案、简单视觉、探索任务可先做再即时检查；一次性脚本若影响数据仍按实际风险验证。
- 每步先测试不是全任务通用规则；避免积累大批未验证修改，也不在每次编辑后无差别重跑全套。

## 6. 实现与收敛
- FAST_FIX 先做 1～2 个最高信息量诊断，首轮最多 3 个诊断问题。按假设计数，不按工具调用；不得把审计包装成一步，或靠改名、切模式、恢复会话重置。
- 未收敛就暂停并列出事实、已排除原因、缺失证据和续查范围。直接相关新事实或用户授权可开启一轮有预算的续查；附近风险或一般不确定性不能自动续杯。诊断预算不限制必要验证，也不允许猜修或虚报。
- 确定直接原因后冻结修复范围；只有当前验收失败、实际副作用或新增证据才扩大调查，不夹带无关重构或未来架构。
- 无信息增量的重复尝试要换方法或报告具体缺口；续查同样必须收敛，不能用一连串各不相同但低价值的检查绕过预算。
- 新依赖、抽象或模块须服务当前行为。沿用现行职责和业务术语，以清楚的对外操作封装相关复杂性，明确数据/规则归属与失败行为；深模块不等于大文件，不能只为文件更小而拆层。
- 不削弱有效断言、伪造通过、用模拟绕过被测边界；需求或测试确有错误才修订，并记录依据。
- 当前任务中，若重复规则、职责错位或接口泄漏实际妨碍实现/可信验证，可在授权范围内做最小局部整理，并以保留行为的回归证据保护；扩大业务/契约仍须相应授权。验收后不另开架构审计，纯清理建议另列。
- 已完成模块不因重新读到旧计划而再次改写；实际新需求、失败证据或相关契约变化才重开，并更新原因。

## 7. 证据与完成
- 必需验收、项目必跑检查和适用风险底线都有当前证据，且无相关已知回归或未解决高风险问题，才报告 GREEN（本范围已证实）。否则说明 NOT GREEN 的具体缺口。
- 证据关联验收、真实命令/观察、结果、环境和被测版本/工作区；后续改动影响到的证据失效，只重验受影响部分。
- 交付先展示可操作的行为及实际运行/演示证据、环境与未验证边界，再链接详细记录；技术切片可用接口结果或命令输出，不强制 UI。文档齐全或测试数量不能代替结果。
- 一片通过不代表全部请求通过；模拟、真实响应回放、真实联调分别标记。软件验收不证明用户需求或商业收益。
- 已接入机器档案的项目，交接/报告完成前按[项目检查协议](scripts/PROJECT_STATE.md)运行 doctor；只读检查不写项目。sync 默认预览，获建档写入授权才用 --write。失败或未适配如实报告，不为“通过”删除验收。
- [证据记录检查器](scripts/check_evidence.py)继续兼容原记录；项目检查额外核对正式验收、依赖、基线版本和总览。记录一致或“证据匹配”不代表断言充分、实际执行已认证或产品 GREEN。
- 只设计报告方案就绪与未决项；只验证报告测试范围。达到当前承诺后停止工具探索，并保存必要的恢复记录。
