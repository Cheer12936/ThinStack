# v0.3.1 交付与验证记录

日期：2026-09-20。发布对象为 `v0.3.1` 标签对应的提交；历史 `v1` 不移动，`v0.3.0` 单独标记其准确快照。

## 行为变化

- 小修复首轮通常只做 1–2 个高信息量诊断，最多 3 个；原因成立后冻结修复承诺，只为直接新证据开启有界续查。
- 方案必须交代目标、范围、关键规则、切片顺序、当前验收、实际设计变化和兼容/证据边界，允许合并表达和引用既有设计。
- 项目初始化的关键问题首轮合并提出，最多再追问一轮；无额外事实时交付条件方案和实施阻塞，不无限续问。
- 项目档案使用一套结构：总览、长期基线和每片从简到详的永久记录。`project_state.py add` 自动分配 `S-001` 这类稳定编号并刷新总览。

## 项目采用

Codex 项目副本安装在 `<project>/.agents/skills/ts-code`，源包仍保持 `allow_implicit_invocation: false`；`--invocation project` 只把该项目副本设为 `true`。

2026-09-20 在 Windows、Codex CLI `0.155.0-alpha.9.2`、`gpt-6-astra` medium 上做了实际烟雾测试：

- 采用项目能发现 Skill，其他项目不能发现该项目副本。
- 不点名 Skill 的库存功能方案任务实际读取了 `SKILL.md`、`proposal.md` 和 `clarify.md`。
- 普通 Python 列表推导式解释未读取 ts-code。
- 执行更新后仍保留 `allow_implicit_invocation: true` 且项目可发现。

这是一台宿主的单次行为验证，不保证所有客户端和模型都做出相同的隐式选择。

## 真实模型回归

固定 `gpt-6-astra` medium、Codex CLI `0.155.0-alpha.9.2`、同一权限和外部预算，对 bare / alpha.11 / v0.3.0 / candidate 各跑一次优惠券本地迁移、新财会方案、跨会话续做和缺少真实联调证据。

首轮 16 次中机械验收 14/16：`v0.3.0` 的迁移案例超时；候选版方案题逐轮追问，四轮后仍未结束。修正后只重跑受影响的方案题：候选版一轮提出 3 个问题后交付条件方案，机械验收通过，用时约 133 秒；同场景 `v0.3.0` 约 198 秒。

组合候选版未受修正影响的三项与方案复测，4/4 机械验收通过，无越界修改、无无依据完成，中位执行时间约 94.6 秒，最长约 133.1 秒。人工审阅确认候选版：迁移只修直接原因并验证列表；方案覆盖七项实质内容；续做保留已完成片；缺联调证据时报告 NOT GREEN。

bare 在这一次小样本中最快且 4/4 机械通过；因此这批数据不支持“Skill 一定更快”或统计性优越的宣称。它支持候选版未重现小修扩成审计、并修正了初始化追问不收敛的发布判断。

机器记录见 [`evals/v0.3.1-validation.json`](../evals/v0.3.1-validation.json)。

## 已知边界

真实模型每组每题仅一次，公开案例可被过拟合，评分器与候选进程处于同一 OS 权限。Token 是 CLI 报告值，未独立认证后端路由。该回归用于发布前发现明显退化，不是生产安全、用户需求或商业价值证明。
